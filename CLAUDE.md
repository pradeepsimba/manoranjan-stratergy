# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **Bank Nifty + Nifty 50 options paper-trading** app (FastAPI), ported from a standalone JS prototype (`c.html`). It streams live 5-minute BankNifty/Nifty 50 index + full-constituent-stock data over WebSocket, evaluates a Top-8 weighted-basket VWAP-momentum + W-OBI execution-filter scalp strategy **tick-by-tick** (2026-09-21 rewrite — see "Current strategy" below; supersedes an earlier leader-momentum + composite-indicator design this paragraph used to describe), decides BUY (long deep-ITM Call) / SELL (long deep-ITM Put), simulates the option leg's premium via **synthetic Black-Scholes pricing** (no real options-chain data anywhere — see "Options pricing" below), and persists everything to PostgreSQL. It also has a **backtest** engine (BankNifty only) that replays the entry side of the identical strategy on historical data.

Single process, single Uvicorn worker by design — all state lives in one in-process singleton (`AppState`). At most **one active trade** at a time (matches the source prototype — no concurrent positions).

**Everything strategy-related is runtime-dynamic.** All tunables (gates, risk, pricing, costs, session timings, tick cadence) are editable live from the `/settings` page — no restart — persisted in the `app_settings` table and re-applied on startup. Backtests accept per-run strategy overrides that never touch live values. See "Dynamic settings layer" below.

## Architecture / daily flow

Driven by `scheduler.SchedulerService._phase_driver` (IST wall clock):

1. **09:00 PRE_MARKET** — no-op. The universe is a static config constant (`cfg.BN_INDEX_TOKEN` + `cfg.BN_ALL_STOCKS`), not fetched — there's nothing that can fail here (unlike the deleted equity engine's Gemini/watchlist screen).
2. **09:15 WAIT_ZONE** — `_load_all_historical()`: fetches 5 days of 5m history for the BN + NF stocks (fully archived, works fine) and MERGES (never replaces) today's BankNifty/Nifty 50 bars into whatever's already accumulated in `st.bn_index_candles_5m`/`st.nf_index_candles_5m` from prior live sessions — see the historical-archive note above. Then `market_data.start()` subscribes to the combined BN (15 tokens, 14 stocks + index) + NF (51 tokens, 50 stocks + index, 11 shared with BN) universe — 55 symbol-interval pairs total, past the server's documented ~40-entries-per-connection buffer limit. Since 2026-09-16/17 (the Nifty 50 universe grew from 32 toward its full 50 official constituents in stages — 3 early additions, LTIMindtree/Nestle India/ONGC, were removed after a vendor query confirmed zero data, and 3 more, InterGlobe Aviation/Jio Financial Services/Max Healthcare, were added after a user-supplied official constituent list and a vendor query both confirmed them — and BankNifty's grew from 11 to its full real membership of 14, after a 2026-09-17 correction against the live NSE factsheet showed the real index has 14 members, not 12, and Union Bank of India/Yes Bank had been miscategorized as non-index "extras"; 11 other non-index banking/financial extras were briefly tracked too but removed the same day per explicit user decision to track only real index members) this is split across **multiple WS connections** (`cfg.WS_MAX_FILTERS_PER_CONN` filters per connection, each with its own independent retry loop) — mirroring the deleted equity engine's split primary/secondary approach. `MarketDataService._process_tick` is fully synchronous (no `await`), so concurrent connections calling it from different asyncio tasks on the same event loop can never interleave mid-update — the existing `threading.Lock`s stay correct unchanged.
3. **09:30–15:00 ACTIVE** (then 15:00–15:30 CUTOFF, exits only) — `_run_active_phase()` is a **tick-wise loop** every `TICK_EVAL_INTERVAL_MS` (default 100ms), running directly on the event loop (no thread pool — only 12 instruments, unlike the equity engine's hundreds):
   - `_tick_exits` — if a trade is open, ratchet the trailing/breakeven stop and check target/stop against the live BankNifty price every cycle (this is also where the live option-premium mark is refreshed for the dashboard — Black-Scholes is closed-form, cheap enough to recompute every 100ms).
   - `_tick_entries` — wall-clock bar-close detection: tracks `st.last_evaluated_bar`; the instant the BankNifty 5m candle list's last bar changes to a NEW bar, evaluates exactly once against that just-closed bar (`bn_entry_exit.evaluate_entry`). No polling/pending-signal latch needed (the deleted JS prototype needed one because it only polled every 3s; 100ms is fast enough to catch a bar close directly).
4. **15:30 CLOSED** — `_run_eod()` squares off any survivor, writes `daily_stats`, **saves today's accumulated BankNifty bars to `bn_index_bars`** (the self-recording archive), persists `funds`, and resets per-day state. **`st.bn_index_candles_5m` is NOT cleared** — see below. `st.candles_5m` (individual stock candles) is **re-fetched via `_load_all_historical()`, not just cleared** (2026-09-16, explicit user decision) — the vendor fully archives multi-day history per stock, so the Stock Candles panel keeps showing real data through the closed session instead of going blank until the next 09:15 reload; a failed re-fetch just leaves the prior day's already-good data in place rather than blanking it.

Strategy core (shared by live **and** backtest, keep it that way): `bn_entry_exit.evaluate_entry` / `evaluate_exit` (BN) and `nf_entry_exit.evaluate_entry`/`evaluate_exit` (NF) → `bn_pricing.*`/`nf_pricing.*` (strike/expiry/premium), pulling in `scalp_signals.py` (basket VWAP score) and `wobi.py` (execution filter). `bn_signals.py`/`nf_signals.py` (the earlier RSI/MACD/EMA/leader-vote gate modules `evaluate_entry` used before the 2026-09-21 rewrite below) were fully DELETED that same day, not merely left unused — see config.py's own note near `BN_SAME_DIRECTION_REQUIRED` (2026-09-23 fix, found in review: a stale copy of that claim used to live here and in `config.py` both, wrongly saying these modules were "left in place, unused... in case this ever needs reverting").

**c.html has no working backtest** (`runBacktest()` there is a confirmed empty stub) — this repo's backtest engine is a fresh design, not a port of anything, but it drives the exact same `evaluate_entry` function the live scheduler calls (see the fidelity limitation below for why `evaluate_exit` itself is NOT shared with backtest).

**Current strategy (2026-09-21, explicit user decision — REPLACES the 2026-09-19 leader-vote rule and its own index-points-target/stop predecessor entirely, for BOTH instruments):** a Top-8 weighted-basket VWAP-momentum entry + deep-ITM strike + W-OBI execution filter + a 12-second premium-based target/stop/time-scratch exit. `evaluate_entry` computes a composite score = `sum(weight_i * (ltp_i - vwap_i)/vwap_i * 100)` over `cfg.BN_SCALP_BASKET`'s (BN) / `cfg.NF_SCALP_BASKET`'s (NF) 8 heaviest-weighted constituents (a 5m-bar typical-price VWAP, not tick-level — see `scalp_signals.py`); fires BUY when score ≥ `+BN_SCALP_SCORE_THRESHOLD`/SELL when score ≤ `-BN_SCALP_SCORE_THRESHOLD` AND the 2 heaviest-weighted basket legs both confirm that direction (`top2_direction_ok`), gated by a trading-window filter (`SCALP_WINDOW1/2_*`, shared by BN and NF — dynamic since 2026-09-23, Settings page's "Scalp Timing" group), a cooldown (`BN_SCALP_COOLDOWN_S`/`NF_SCALP_COOLDOWN_S`), and a daily trade cap (`SCALP_MAX_TRADES_PER_DAY`). The fired signal's strike is a DEEP-ITM strike (`bn_pricing.get_itm_strike`/`nf_pricing.get_itm_strike`, offset `BN_ITM_OFFSET_POINTS`/`NF_ITM_OFFSET_POINTS` from spot — **not** the true ATM strike; see the "Naming fix" note below), gated by a W-OBI (weighted order-book imbalance) execution filter on that option's own synthetic depth clearing `BN_WOBI_MIN_RATIO`/`NF_WOBI_MIN_RATIO` (`app/engine/wobi.py` — a documented synthetic proxy, not real market depth; there is no real option order book anywhere in this repo). Always exactly 1 lot (`cfg.BN_LOT_SIZE`/`NF_LOT_SIZE`) — no position sizing formula, unlike the old equity engine's risk-based `calc_quantity`. `BN_SAME_DIRECTION_REQUIRED` (the old 9-of-14 leader-vote threshold) survives in `config.py` only because `app/backtest/signal_study.py` — a standalone historical-analysis tool, never called by `evaluate_entry`/`evaluate_exit` — still reads it for its own "what would the old rule have done" study.

**Exit (2026-09-21 rewrite — REPLACES the old index-points target/stop/breakeven/trailing state machine entirely):** a hard 12-second-by-default (`BN_SCALP_TIME_STOP_S`/`NF_SCALP_TIME_STOP_S` — dynamic since 2026-09-23, Settings page's "Scalp Timing" group; frozen onto the trade at entry like every other risk parameter) bracket on the OPTION PREMIUM itself (₹, not index points) — `target`/`current_sl` are absolute premium levels frozen at entry as `entry_premium + target_rs`/`entry_premium - stop_rs` (`BN_SCALP_TARGET_RS`/`STOP_RS`, `NF_SCALP_TARGET_RS`/`STOP_RS`); if neither is touched before the time-stop elapses, force a TIME_SCRATCH exit at a marketable, spread-crossing price (`premium - scratch_slippage_rs`, frozen from `BN_SCALP_SCRATCH_SLIPPAGE_RS`/`NF_SCALP_SCRATCH_SLIPPAGE_RS` at entry the same way — 2026-09-23 fix, found in review: this used to read `cfg` directly at exit time instead of from a frozen trade field, the one risk parameter that had been missing from the entry-freeze convention every other parameter here follows). `breakeven_trigger`/`trail_trigger`/`trail_distance`/`stoploss_points` are now vestigial fields (always 0.0), kept only so `BNTrade`/`NFTrade`/`BTPosition` stay duck-type compatible with any code that still constructs a trade the old way. Settlement is the **option premium P&L × lot size** (`(exit_premium - entry_premium) * lot_size`) — the underlying's index-price move is kept on the trade only as a diagnostic (`index_pnl_points`), never part of P&L.

***Backtest fidelity limitation (2026-09-21):*** this repo has no historical market data at sub-5-minute granularity, so the live strategy's 12-second exit lifecycle cannot be faithfully replayed — `app/backtest/engine.py`'s `_try_exit` does NOT call the shared `evaluate_exit`/`finalize_exit`; it independently resolves each position using the entry bar's immediate next bar's OHLC-implied premium range (gap-at-open + intrabar high/low touch, via `app/backtest/fills.resolve_premium_touch` — a coarse proxy for "did target/stop get touched sometime in the ~5 minutes after entry," not a faithful sub-bar simulation) and forces a TIME_SCRATCH at that bar's close if neither was touched. Treat backtest ₹ P&L/win-rate for this strategy as a rough proxy, not a faithful replay. This is a real, documented architectural gap (`_try_exit` re-forking the exit decision instead of sharing `evaluate_exit`), not something to silently "fix" by making it call the shared function — that would need a larger redesign (`BTPosition` would need real tick-level data `evaluate_exit` doesn't require but this repo doesn't have). (`fills.resolve_index_touch`, the OLDER index-points touch resolver from before this rewrite, was DELETED 2026-09-23 as confirmed-dead code — zero remaining callers once `resolve_premium_touch` above fully superseded it.) **Look-ahead fix (2026-09-23, found in review):** `_try_exit`'s IV lookback used to include the CURRENT bar's own close (`bn_ss.closes[...:gidx + 1]`) even though the touch check can resolve at that same bar's OPEN — a real look-ahead bug (pricing an open-gap touch using a return only knowable once the bar had fully closed), the same class of bug already fixed on the live side (`closed_tail_closes` excluding the still-forming bar). Fixed to `[...:gidx]` (excludes bar `gidx`'s own close) — this affected essentially every simulated trade's exit pricing, not an edge case. The entry-side lookback and the EOD square-off's lookback are UNCHANGED and correctly still include their own bar (an entry decision, and an EOD settlement, are each made using that same bar's own close — not a look-ahead in that context). Nifty 50 has no backtest coverage at all — `app/backtest/engine.py` only ever imports `bn_entry_exit`/`bn_pricing`. **`BN_SCALP_TIME_STOP_S`/`NF_SCALP_TIME_STOP_S` are `bt: False` (2026-09-24, found in review):** a direct consequence of the fidelity gap above — `_try_exit` never reads `BTPosition.time_stop_s` (it always resolves on the entry bar's immediate next bar regardless), so offering this as a per-run backtest override used to silently do nothing; disabled in `app/services/settings.py`'s SPEC rather than the larger redesign this section already rules out. **Incomplete-recording days are excluded, not simulated (2026-09-24, found in review):** `bn_index_bars` has no guarantee any given day has a full ~75-bar session — a live-engine restart/outage mid-session leaves that day with only however many bars were recorded before it stopped. `app/backtest/engine.py`'s `simulate()` now drops any day with fewer than `MIN_DAY_BARS` (20) BankNifty bars from the run entirely (logged, not silent) — previously such a day was simulated like any other, EOD-squaring off a survivor at whatever its last available bar happened to be (e.g. 10:05 IST) and mislabeling that exit `"EOD"` as if it were a genuine end-of-session close, silently distorting that day's P&L/win-rate. Also hardened the same day: `load_backtest_data`'s vendor REST fetch for the 14 BN stocks swallows any HTTP/network failure into an empty dict rather than raising (see `historical_data.py`'s `_fetch`) — `run_backtest` now hard-fails the run (matching the existing `bn_index is None` hard-fail just above) if any `BN_SCALP_BASKET` token's stock history is missing, instead of silently completing as a misleading `total_trades: 0` result (every basket leg missing means the score is structurally always 0.0, indistinguishable from "the strategy genuinely found no setups").

**Options pricing — fully synthetic, no real option-chain data:** ATM strike = `round(spot/100)*100`; expiry = **the LAST TUESDAY of the current/next month, 15:30 IST** (`bn_pricing.get_next_expiry` — see the expiry-day note below; this was "next weekly Thursday" until a 2026-09-19 fix); premium = standard Black-Scholes off BankNifty spot + a realized-volatility estimate from its own 5m bar-close log-returns (annualized via 75 bars/day × 252 days/year — a deliberate deviation from the source's tick-based estimator, required so live and backtest can share one `estimate_iv` implementation; backtest has no tick stream to replay). Risk-free rate, IV bounds, and default IV are all dynamic settings. See `app/engine/bn_pricing.py`. Nifty 50's own `nf_pricing.get_next_expiry` is a SEPARATE function (next Tuesday, weekly) — see the expiry-day note below for why these two genuinely diverged and are no longer shared.

**Expiry-day fix (2026-09-19, confirmed via web search + a real user-supplied example option symbol):** NSE changed its index-options expiry-day convention effective 2025-09-01 — Nifty 50 weekly expiry moved from Thursday to **Tuesday**, and **BankNifty's weekly contracts were discontinued entirely**, leaving only monthly/quarterly, with that expiry day also moved to the **last Tuesday** of the month. `bn_pricing.get_next_expiry`/`nf_pricing.get_next_expiry` were still using the old "next Thursday, weekly" rule for BOTH instruments until this fix — a real correctness bug affecting every Black-Scholes premium calculation in the engine (live and backtest), not just the option-symbol/real-LTP features. Because the real-world cycles now genuinely differ (BN monthly vs. NF weekly), `get_next_expiry` and the option-symbol builder are no longer shared between the two pricing modules — `bn_pricing.build_monthly_option_symbol` (`UNDERLYING+YY+MMM+STRIKE+CE/PE`, e.g. `"BANKNIFTY26SEP56400CE"`, no day-of-month since a monthly contract's expiry day is implied) vs. `nf_pricing.build_weekly_option_symbol` (`UNDERLYING+YY+M+DD+STRIKE+CE/PE`, `M` a single-char month code 1-9/O/N/D, e.g. `"NIFTY2692223250PE"` — confirmed correct against a real user-supplied example). Reusing one function for both would silently be wrong for whichever one changed — don't re-merge them.

**Self-recorded BankNifty history:** because the market-data server never provides BankNifty index history via the REST API (see above — now returns nothing at all, not even "today"), `scheduler._run_eod` writes the day's accumulated `bn_index_candles_5m` buffer into the `bn_index_bars` table every day (idempotent upsert by `start_time`) — since 2026-07-23 this buffer is populated by the synthetic index (see above) rather than real vendor ticks, but the recording pipeline itself is unchanged. `app/backtest/data.load_backtest_data` reads BankNifty history **from this table**, not from the REST API — the runnable backtest date range grows by one day at a time as the live engine runs, now backed by synthetic bars for any day recorded after the migration. The 14 BN stocks ARE fully archived on the external server, so they're still fetched directly for every backtest run.

## Dynamic settings layer

- `app/config.py` holds **static** system values (endpoints, DSN, the BN instrument universe, pool/buffer sizes, lot size) as plain attributes, and **dynamic** tunables in `_DEFAULTS`, resolved via module `__getattr__` with precedence: *thread-local overrides (backtest run) → runtime overrides (Settings page / DB) → default*. `cfg.X` therefore always returns the current value.
- **Never copy a dynamic `cfg.X` into a module-level constant or default-argument value** — it freezes at import and silently stops being dynamic. This is why `BNTrade`/`BTPosition` **freeze** their risk parameters (target/stoploss/breakeven/trail) from cfg exactly once, at entry (`bn_entry_exit.open_trade_from_signal`) — that's a deliberate snapshot for correctness (an open trade's economics must not shift under it), not the anti-pattern the rule above warns about.
- **Adding a tunable = two places:** a default in `config._DEFAULTS` **and** a SPEC entry in `app/services/settings.py` (label/type/bounds/group/`bt` flag). Time-of-day settings are virtual `"HH:MM"` SPEC keys expanded to their `*_HOUR`/`*_MIN` config pairs. An import-time assertion in `settings.py` raises `RuntimeError` if the two ever drift.
- `cfg.thread_overrides(...)` may only be entered in a thread that shares memory with the live event loop and must never leak into it — as of 2026-09-23 (see the day-level parallelism note below) nothing in this repo actually calls it any more; day workers are separate OS PROCESSES now, and `cfg.set_runtime_overrides` inside a dedicated worker process can't leak into the live server's own `cfg` state by construction (no shared memory), so the thread-local mechanism `thread_overrides` exists for became unnecessary. Kept as generic infrastructure, not deleted, in case a future thread-based per-call override need reappears.
- Backtest per-run overrides: `POST /api/backtest {overrides: {SPEC_KEY: value}}`, validated with `expand_changes(bt_only=True)` (only `bt: True` SPEC entries), recorded in `backtest_runs.params`, applied inside each day-worker PROCESS via `app.backtest.engine._pool_worker_init` (see the day-level parallelism note below) — filtered to known dynamic keys only, so a key that somehow isn't a genuine dynamic tunable is silently dropped rather than crashing the whole process pool (matches the old thread-based mechanism's silent-ignore behavior, since a bad key was never actually reachable in practice — the API layer's own validation already filters before this point).
- Settings API: `GET /api/settings` (grouped describe), `PUT /api/settings {changes}` (validate → persist atomically (`replace_app_settings`, one transaction) → apply; a value equal to its default deletes the override row), `POST /api/settings/reset {keys?}`. As of 2026-09-23, the "Scalp Timing" group's two trading windows are cross-validated (`settings._validate_scalp_windows` — start must be before end for each window) on save, on partial reset, and at startup load (self-heals: an invalid stored combo reverts the whole group to defaults rather than crash-looping). (The 2026-09-09 settings purge removed the session-time/indicator-period tunables an earlier version of this doc described here — `validate_time_order`/`validate_bn_indicator_periods` no longer exist; `_validate_scalp_windows` is a fresh, narrower replacement scoped to just the 2 windows this section re-added.)

## Authentication

**Added 2026-09-24 to this doc — found in review to be entirely undocumented despite being a real, deployment-critical subsystem** (ported from a sibling project, `kotak-neo-order-tool`'s `app/web/auth.py`). A single shared username/password gates every page and API route (`main.py`'s `require_login_page`/`app/api/dashboard.py`'s router-level `require_login`, both in `app/auth.py`) — **except** `/ws/dashboard` (explicit user decision, so the live price feed doesn't depend on a logged-in tab), `/login`, and `/healthz` (the Dockerfile's `HEALTHCHECK` curls this from inside the container with no credentials).

- **Session:** a signed (`itsdangerous`), 12-hour cookie (`COOKIE_NAME = "session"`) — no server-side session store. `_serializer()` **fails closed**: an unset `SESSION_SECRET` raises a 500 on every gated request rather than silently allowing access or signing against an empty key. `secure=True` is set dynamically off `request.url.scheme == "https"` (read via `X-Forwarded-Proto`, since this app is always plain HTTP behind nginx/Caddy in the documented deployments — see the Dockerfile's `--forwarded-allow-ips` note) rather than hardcoded, so login still works for a direct `python main.py` local run with no reverse proxy in front. `samesite="strict"` is this app's only CSRF defense (no CSRF token anywhere) — safe since the login flow never needs the cookie sent cross-site.
- **Credentials:** `SETTINGS_USER`/`SETTINGS_PASSWORD`/`SESSION_SECRET` env vars (`app/config.py`; `docker-compose.yml` passes them through explicitly since `main.py`'s `load_dotenv()` can't see this project's `.env` from inside the container). `check_credentials` always runs BOTH the username and password `hmac.compare_digest()` calls, never short-circuiting on a failed username — an `and`-short-circuit would leak which one was wrong through timing despite each individual compare being constant-time.
- **Lockout:** `LoginAttemptLimiter` (`app/auth.py`) — 5 failed attempts from one source IP locks that IP out for 15 minutes, in-memory only (correct for this app's single-instance deployment, not distributed-safe). `allow()` checks AND reserves the attempt under one lock acquisition specifically so a burst of concurrent requests from the same IP can't each pass the check before any records a failure.
- **Routes:** `GET/POST /login` (`static/login.html` + form POST → redirect), `GET /logout` (clears the cookie), both in `main.py`, not `app/api/dashboard.py`.

## Hard conventions — get these wrong and it breaks

- **Keying:** `candles_5m` is keyed by **TOKEN** (trading-symbol string) — the 14 BN stocks only, the real NIFTY BANK index's full membership (2026-09-16 addition of Bank of Baroda/Union Bank of India/Yes Bank + a 2026-09-17 correction; 11 non-index banking/financial extras were tracked briefly the same day then removed, per explicit user decision to track only real index members); the BankNifty index has its OWN dedicated field, `bn_index_candles_5m` (a plain list, not a dict), with its own lock `st._bn_index_lock`. `ltp` is keyed by **SYMBOL NAME**; the index's live price is the separate `st.bn_index_ltp` float. Don't conflate the two — there is deliberately no extra entry in `candles_5m`/`ltp` for BankNifty itself.
- **`st.bn_index_candles_5m` is never cleared at EOD** (unlike everything else, which resets daily) — it's the ONLY source of multi-day BankNifty depth (the composite indicator gate needs `BN_INDICATOR_LOOKBACK_BARS`, default 200, bars to converge; the external server can never supply more than ~75 bars/day). It persists and grows across real trading days within one long-running process, capped at `MAX_CANDLE_BUFFER` (300 bars, ~4 sessions). A restart loses it; `_load_all_historical`'s merge-not-replace logic (via `MarketDataService._upsert_list`) is what lets it survive a same-process day rollover.
- **Single active trade.** `st.active_trade: Optional[BNTrade]` — not a dict. Closing sets it to `None` and appends to `st.closed_trades`. There is no concurrent-position concept anywhere in this engine (deliberately, matching the source).
- **Locking:** `candles_5m` token locks and `_bn_index_lock` guard the WS-thread-vs-event-loop boundary — `MarketDataService._process_tick` (WS callback context) and the scheduler's tick loop are the only two touchpoints, and both go through `st.candle_lock(token)` / `st._bn_index_lock`.
- **Candle lists are strictly chronological.** `market_data._upsert`/`_upsert_list` update the in-progress bar on an equal `start_time`, append on a newer one, and **drop** stale out-of-order bars (reconnect replays). `_load_all_historical`'s catch-up merge reuses `MarketDataService._upsert_list` directly (not a second copy) so there's exactly one implementation of "how a BankNifty bar gets folded in," whether it arrives via WS tick or REST catch-up.
- **TA-Lib was removed entirely (2026-09-24, found in review, acted on after being flagged-but-deferred once already on 2026-09-23):** `bn_signals.py`/`nf_signals.py` (the only callers of `talib`'s RSI/EMA — the composite-indicator gate's MACD was two plain `talib.EMA` calls subtracted, never `talib.MACD`) were fully deleted 2026-09-21; a repo-wide grep confirmed zero remaining `talib` imports anywhere, re-confirmed independently across several later review rounds. `TA-Lib` is no longer in `requirements.txt`, and the Dockerfile no longer compiles its native C library or installs `build-essential`/`wget` for that purpose — every rebuild used to pay for a full native C compile (plus those build tools staying baked into the final runtime image) for a dependency nothing imported any more.
- **Shared decision core, not just shared formulas:** `bn_entry_exit.evaluate_exit` reads risk parameters (target/breakeven/trail) FROM THE TRADE OBJECT it's given, not from `cfg` — and it's called with either a live `BNTrade` (`app/models.py`) or a backtest `BTPosition` (`app/backtest/portfolio.py`) interchangeably, because the two dataclasses share the exact field names `evaluate_exit` touches (`direction`, `entry_index_price`, `current_sl`, `sl_stage`, `target`, `trail_trigger`, `trail_distance`, `breakeven_trigger`, `strike`, `option_type`, `expiry`). Don't rename a field on one without the other — this duck-typing is how backtest and live stay provably in sync without a shared decision function needing two call signatures.
- **No look-ahead in backtest:** at bar `t` an entry uses only bars `[..t]`; IV/expiry/premium are computed from bar `t`'s own timestamp and closes `[..t]` only. A position opened at bar `t` exits only on bars `> t`. Backtest is **intraday-only** (fresh portfolio per day, EOD square-off, days run in parallel across real OS processes — see below) — there is no positional/delivery/1d mode (nothing in the source ever holds an option position overnight).

**Backtest day-level parallelism is real OS processes, not threads (2026-09-23, explicit user request — "lightning fast" performance pass).** `app/backtest/engine.py`'s `simulate()` used to fan days out across a `ThreadPoolExecutor`; since each day is genuinely independent (fresh `Portfolio()`, no shared mutable state) this is embarrassingly-parallel CPU-bound work, but Python's GIL meant those "parallel" threads barely helped — per-bar `evaluate_entry`/Black-Scholes work is mostly pure-Python/small-numpy-array work the GIL serializes across threads regardless of thread count. Switched to `ProcessPoolExecutor` with `multiprocessing.get_context("spawn")` (Linux's default `fork` is unsafe here — this server has an open asyncpg pool and live WebSocket connections that a fork could corrupt; `spawn` boots a genuinely fresh interpreter instead). Benchmarked on a synthetic dataset before committing: a ~1-year (250 trading day) backtest went from 83s (threads) to 28s (processes) — **2.96x**, with bit-for-bit identical trade count and net P&L confirmed between both implementations; a short 60-day range only gained ~1.1x, since spawning worker processes has real fixed startup cost that needs enough per-worker work to amortize.

Two hazards specific to embedding `ProcessPoolExecutor` inside a *live* ASGI server (not a standalone script) were verified empirically, not assumed: (1) `spawn` does **not** inherit the parent's `app.config` module state, so a live Settings-page override would silently vanish from backtest runs unless forwarded explicitly — `simulate()` snapshots `{k: getattr(cfg, k) for k in cfg.dynamic_defaults()}` in the parent (which still sees the live value) and `_pool_worker_init` applies it via `cfg.set_runtime_overrides` in each child before that run's own per-run `overrides` layer on top; confirmed by directly probing a spawned worker's `cfg.X` value after setting a live override in the parent. (2) Spawning workers whose target function lives in `app.backtest.engine` does **not** re-trigger `main.py`'s FastAPI-app/service creation in the children **under the Docker/production launch** (`uvicorn main:app`, where `main.py` is imported as an ordinary module) — pickling-by-reference only needs to import the target function's own module and its dependency tree there. **Correction (2026-09-23, found in review):** this does NOT hold for the LOCAL dev launch this same doc documents (`python main.py`) — run that way, `main.py` executes as `__main__` in script mode, and Python's `spawn` bootstrap unconditionally re-execs that script's top-level code in every child (as `__mp_main__`, to reconstruct `sys.modules['__main__']`) regardless of what the pickled target actually needs — confirmed with a standalone repro. This DOES re-run `main.py`'s `DatabaseService()`/`MarketDataService()`/`FastAPI()` construction in every worker under local dev (harmless — no I/O side effects in those constructors, and `uvicorn.run(...)` itself stays skipped since it's behind `if __name__ == "__main__":`, false for `__mp_main__`) — but it's real wasted per-worker startup work, not the "zero re-trigger" the previous version of this note claimed. A third, narrower thing found only while benchmarking: `cfg.set_runtime_overrides` raises on an unknown key (unlike the old `cfg.thread_overrides`, a plain unvalidated thread-local dict merge) — since an initializer exception breaks the *whole* pool, `_pool_worker_init` filters `overrides` to known dynamic keys first, so a stray invalid key can't take down an entire run (this should never actually trigger given the API layer's own upstream validation, but the blast radius of an initializer exception is much bigger than a single silently-ignored key ever was).
- **Options are cash-only, always exactly 1 lot** — there is no leverage/margin concept and no quantity-sizing formula anywhere in this engine (unlike the deleted equity engine's `calc_quantity`/`INTRADAY_LEVERAGE`).

Strike/expiry/premium are computed server-side via the real `bn_pricing.py`/`nf_pricing.py` (ATM strike off the live spot, realized-vol IV estimate) — there is no client-side pricing preview anymore, and like an algo-fired trade it also picks up the real-option-LTP feature below once a tick arrives. Order Type (Market/Limit) is cosmetic only: every fill in this engine is a synthetic Black-Scholes mark at submit time (until a real tick arrives), there's no real order book for a limit price to rest on. `js/kiteForm.js` uses the same `ids`-object pattern as `STOCK_IDS_BN`/`STOCK_IDS_NF` etc. elsewhere (`KITE_IDS_BN`/`KITE_IDS_NF`) rather than a second copy of the file.

Its IndexedDB store is keyed by a derived `localId` (`${orderId}_ENTRY`/`${orderId}_EXIT`) and written with `put()`, not `add()` — a page reload always re-delivers the current trade state, so idempotent overwrite (not an in-memory dedupe set, which can't survive a refresh) is what prevents duplicate rows.

**Live entry-ITM CE/PE quote (2026-09-18, explicit user decision; fields renamed `atm_*`→`itm_*` 2026-09-23, see below)** — `evaluate_entry` (in both `bn_entry_exit.py`/`nf_entry_exit.py`) now computes the deep-ITM strike the strategy would actually trade (`get_itm_strike`, offset by `BN_ITM_OFFSET_POINTS`/`NF_ITM_OFFSET_POINTS` from spot) and its Black-Scholes CE/PE premiums UNCONDITIONALLY, every closed bar, regardless of whether the entry gates actually pass — previously this was only computed inside the `if buy_ready or sell_ready:` block, so it stayed blank almost all the time. Exposed on `BNDiagnostic`/`NFDiagnostic` as `itm_ce_premium`/`itm_pe_premium` (alongside `itm_strike`/`itm_iv`; `itm_premium` is kept as a CE-value alias for the still-unused Entry Loop Monitor UI), sent in `STATE_UPDATE`'s `entryLoop`/`entryLoopNf.itmCePremium`/`itmPePremium`. This is a theoretical Black-Scholes estimate only, not real option-chain data.

**Naming fix (2026-09-23, found via a user-reported dashboard screenshot):** these fields used to be named `atm_strike`/`atm_premium`/`atm_ce_premium`/`atm_pe_premium`/`atm_iv` and were rendered in the dashboard as `ATM {strike}` — but they were never the true at-the-money strike; they always held the deep-ITM strike/premium above (a leftover from before the 2026-09-21 scalp rewrite, which repurposed these fields for ITM values without renaming them). This produced a real, visible discrepancy: the dashboard's "no active trade" panel showed one strike labeled `ATM` (actually ITM, e.g. `23200`) right next to the separate live ATM CE/PE watchlist below showing a *different*, genuinely-ATM strike (e.g. `23400`) with a real market LTP — confusing, since both looked like they should represent "the current ATM." Renamed throughout (`app/models.py`'s dataclasses, `bn_entry_exit.py`/`nf_entry_exit.py`'s diagnostic construction, `scheduler.py`'s `_diag_dict` JSON keys, `dashboard.js`'s two render sites) to `itm_strike`/`itm_premium`/`itm_ce_premium`/`itm_pe_premium`/`itm_iv`, and the dashboard label changed to `Entry ITM {strike}` — purely a naming/labeling fix, no calculation changed (nothing here ever fed settlement/P&L).

**Live ATM CE/PE watchlist (2026-09-18, explicit user decision)** — a continuous REAL-market-LTP subscription for whatever the CURRENT at-the-money strike is, shown regardless of whether a trade is open. Distinct from the real-option-LTP paper-trading feature above: that one tracks ONE trade's option symbol, FROZEN at the strike it entered on; this one tracks the LIVE, moving ATM strike, recomputed continuously off `st.bn_index_ltp`/`nf_index_ltp`. `SchedulerService._tick_atm_watch` runs every `TICK_EVAL_INTERVAL_MS` tick (cheap — `get_atm_strike` is just `round(spot/100)*100`, no Black-Scholes) but only touches the WS subscription when the strike actually changes, via `MarketDataService.set_bn_atm_watch`/`set_nf_atm_watch` on the same dedicated option WS connection `_resync_option_connection` manages (the per-trade feature's `_bn_option`/`_nf_option` slots that used to share this connection were removed 2026-09-22 — see "Real-option-LTP paper trading" below — so this watchlist is now the connection's only occupant). `_process_tick` matches ticks against `st.bn_atm_ce_symbol`/`bn_atm_pe_symbol`/`nf_atm_ce_symbol`/`nf_atm_pe_symbol`, writing into `st.bn_atm_ce_ltp`/`bn_atm_pe_ltp`/`nf_atm_ce_ltp`/`nf_atm_pe_ltp` — no one-way latch here (unlike the per-trade feature), since there's no single trade's entry value to freeze; a strike change always resets the cached LTPs to `None` rather than showing a stale, wrong-strike price. Sent in `STATE_UPDATE` as `bnAtmWatch`/`nfAtmWatch` (`{strike, ceSymbol, peSymbol, ceLtp, peLtp}`), rendered by `dashboard.js`'s `renderAtmWatch()` — a small always-visible watchlist row per Active Trade panel, showing "waiting for live tick" until the first real tick for that strike arrives. Torn down at EOD (`_run_eod` calls `set_bn_atm_watch(None, None)`/`set_nf_atm_watch(None, None)`) — no point holding a subscription for a stale strike once the market's closed.

**Server-side price alerts (`app/services/price_alerts.py`)** — the leader-consensus price-move alert (N of BN's 6 / NF's 12 leaders each crossing their own `BN_PRICE_ALERT_PTS_*`/`NF_PRICE_ALERT_PTS_*` points threshold, in the SAME direction, on the same live bar) used to be computed entirely client-side, once/sec, off `STATE_UPDATE` — meaning it only ran while a dashboard browser tab was open, and could miss a fast in-and-out move between STATE_UPDATE ticks. As of 2026-09-09 (explicit user decision) the check itself moved server-side into `SchedulerService._tick_alerts`, called every `TICK_EVAL_INTERVAL_MS` tick alongside `_tick_exits`/`_tick_entries` — same cadence and same `st.candles_5m` read path the trading engine itself uses, just a separate, purely-informational check that never touches `evaluate_entry`/`evaluate_exit`. When the condition fires, the server pushes an `ALERT` WebSocket message (see the table below); the browser's job (`static/js/alerts.js`'s `handleServerAlert`) is now just to display it. The edge-trigger state (`_was_consensus`, keyed `"BankNifty:up"` etc.) lives as module-level state in `price_alerts.py` — safe unlocked because, like `st.last_evaluated_bar`, it's only ever touched from the tick loop on the event loop, never from the WS ingest thread. The client still independently computes the SAME per-leader crossed/direction data purely for the live "X/N leaders crossed" badge next to the Global Signal (`checkPriceAlerts`/`_renderThresholdBadge` in `alerts.js`) — that's cosmetic display only, not the alert-firing path anymore.

**Edge-state commit gate (2026-09-23, found in review):** `check_consensus` used to update `_was_consensus` unconditionally every tick, regardless of whether any browser was connected (`SchedulerService._tick_alerts` only gated the BROADCAST on `self._ws.count() > 0`, not the state update). This silently defeated the "independent of whether/how often any browser is watching" claim above: an edge detected with zero clients connected got "consumed" right there — a client connecting later, while the condition was STILL true, would see `met=True, was=True` (no new edge) and never get notified at all. Fixed by adding a `has_clients` param to `check_consensus`, passed as `self._ws.count() > 0` from `_tick_alerts` — detection still runs every tick regardless of client count (unchanged), but the `_was_consensus` COMMIT is skipped while `has_clients` is `False`, so the first check after a client (re)connects correctly sees a fresh edge if the condition is still active.

**Real-option-LTP paper trading — REMOVED 2026-09-22 (explicit user decision).** This feature existed 2026-09-17 through 2026-09-21: both automated engines settled trade P&L off the option's real market LTP instead of a purely theoretical Black-Scholes mark, wherever a real tick was available, via a one-way `trade.premium_synthetic` latch flipped by `MarketDataService._process_tick` matching a tick against `active_trade.option_symbol`. It was removed after the 2026-09-21 scalp-strategy rewrite made it a genuine bug: a real tick could arrive within the same second a trade opened (especially with a repeated strike, since the option WS subscription might already be flowing) and snap the settlement premium straight past the new strategy's whole **~₹2-3 target/stop bracket** — confirmed root cause of a real production incident (same-second entry/exit at a huge, inconsistent loss with the index barely moving). The old, much wider index-points bracket could absorb that discontinuity; this one can't. Settlement is now consistently the synthetic Black-Scholes mark for a trade's entire life — see `bn_trade.check_tick_exit`'s docstring for the full writeup.

What's left of it: nothing — the whole mechanism was removed outright, not left dead. `_process_tick` no longer matches ticks against `active_trade.option_symbol` (only the separate ATM watchlist match below remains); `BNTrade`/`NFTrade.premium_synthetic`, `MarketDataService.set_bn_option_symbol`/`set_nf_option_symbol`/`_bn_option`/`_nf_option`, and `AppState.market_data_service`/`bn_option_ltp`/`nf_option_ltp` were all fully deleted (fields, methods, and the self-registration that only existed to reach them) once a repo-wide grep confirmed zero remaining readers anywhere — Python or JS. (An earlier pass had left some of these in place with a "kept in case a future feature reuses it" rationale; that was superseded once it turned out the actual justifications given — e.g. "AppState fields are read in several places by attribute name" — didn't hold up under a real grep.) `evaluate_exit`'s `live_premium_override` parameter was deleted from both `bn_entry_exit.py`/`nf_entry_exit.py`. `_resync_option_connection`'s third WS connection itself is still very much alive — it's now driven ONLY by the live ATM CE/PE watchlist below, which was never part of this removal.

Facts about the vendor protocol worth keeping even though the feature that needed them is gone: this vendor streams real option data, but **only at 1-minute granularity**, never 5m; and an option filter's `stockname` must be the underlying's plain name ("NIFTY"/"BANKNIFTY"), not the option symbol repeated. If anything ever resubscribes to option ticks again, both of those still apply.

Backtest was never affected either way: `BTPosition` (`app/backtest/portfolio.py`) has no `option_symbol`/`premium_synthetic` fields, and nothing in the backtest replay loop calls `market_data.py` or `bn_trade.py`/`nf_trade.py` (those are live-only, under `app/services/`) — it has always used the pure Black-Scholes model.

The `/ws/dashboard` endpoint broadcasts three distinct message shapes — `dashboard.js`'s `ws.onmessage` dispatches on `type`:

| `type` | Cadence | Payload |
|--------|---------|---------|
| `STATE_UPDATE` | 1 s | Full dashboard payload: `clock`, `phase`, `wsStatus`, `apiStatus`, `bnLtp`, `dailyPnl`, `funds`, `activeTrade`, `closedTrades`, `entryLoop` (the `BNDiagnostic` — the "why didn't it fire" panel), `stockCandles`/`globalSignal`/`weightedRedGreen`/`breakout` (BN + NF), etc. |
| `TICK_UPDATE` | ~100 ms | `{prices: {name: ltp, ...}}` — a live-price delta, feeds the Stock Candles panel's live cell flash + the local qty-audit IndexedDB log (`static/js/breakout.js`/`qtyAudit.js`) |
| `ALERT` | on fire (edge-triggered) | `{title, body}` — pushed by `SchedulerService._tick_alerts` (via `app/services/price_alerts.py`, checked every `TICK_EVAL_INTERVAL_MS` tick) the instant the leader-consensus price-move condition fires; `static/js/alerts.js`'s `handleServerAlert` just displays it as a browser Notification/toast. Moved server-side 2026-09-09 (explicit user decision) so it no longer depends on a dashboard browser tab being open to notice — see the "Server-side price alerts" note below. |

## Gotchas & known limitations

- **The BankNifty history-archive limitation (see "External dependencies" above) is the single most important thing to remember when touching backtest or the historical loader.** If a backtest run fails with "no self-recorded BankNifty history," that's expected until the live engine has run at least one full day in this environment — it is NOT a bug to "fix" by fetching a date range from the REST API.
- **Kotak Bank naming:** `cfg.BN_ALL_STOCKS["KOTAK BANK"] = "KOTAKBANK"` — the dict KEY (stockname text) must be `"KOTAK BANK"`, NOT `"KOTAK MAHINDRA BANK"`. The market-data server matches by exact stockname text; confirmed by direct testing that the "Mahindra" variant silently returns zero candles for the identical, correct token/symbol.
- **South Indian Bank naming (same gotcha class, 2026-09-17):** if `"THE SOUTH INDIAN BANK"` (note the leading "THE", per the vendor's own instrument-master export) is ever re-added to `cfg.BN_ALL_STOCKS`, use that exact text — it's not currently tracked (removed 2026-09-17 along with 10 other non-index banking extras, once the real NIFTY BANK index was confirmed to have 14 members, not 12; see the Architecture section above), but was live-tested at the time and worked fine under that name.
- **The vendor doesn't yet carry the CURRENT week's Nifty 50 option series (confirmed 2026-09-23, NOT a code bug):** the live ATM CE/PE watchlist's Nifty panel can sit on "waiting for live tick" indefinitely while the BankNifty panel next to it gets real ticks fine. Root-caused by directly querying the vendor's REST historical-data endpoint outside this app entirely: `NIFTY2692223250PE` (last week's, since-expired Sept-22 contract) returns real 1m candles, but `NIFTY269292…CE/PE` (the just-rolled Sept-29 contract) returns **zero candles at every strike tested** (23000 through 24000) — both historically and live, and independent of `stockname` variant (`"NIFTY"` vs `"NIFTY 50"`). This rules out a symbol-format or subscription bug (`nf_pricing.build_weekly_option_symbol`'s format is confirmed correct — it's what fetched last week's contract fine) — the vendor's data source simply hasn't populated the newly-rolled weekly series yet. Nothing to fix in this repo; if it recurs, verify with a direct REST query (bypass the app, same pattern as this note) before suspecting the symbol builder or the WS matching logic in `market_data.py`.
- **Entry is evaluated every tick, not once per bar (2026-09-22, explicit user decision — supersedes the composite-indicator-gate-era claim that used to be here).** `evaluate_entry` (BN and NF alike) is called every `TICK_EVAL_INTERVAL_MS` (~100ms) from `_tick_entries`/`_tick_entries_nf`, not gated on a bar closing — the old `last_evaluated_bar`/`last_trade_candle` dedup state was removed (`state.py`). The basket VWAP-momentum score's "current price" side now reads the LIVE tick (`current_index_price`/`basket_ltp` params, fed from `st.bn_index_ltp`/`st.ltp`), so a real move can fire a trade within ~100ms instead of waiting up to 5 minutes for the next bar close; VWAP itself still only moves at bar-close granularity (see `scalp_signals.py`). Re-entry after a fire is still fully gated by `st.active_trade is not None` plus the cooldown check inside `evaluate_entry`, so there's no risk of firing twice off one persistent signal. Backtest is unaffected — it never passes `current_index_price`/`basket_ltp` (no tick stream to give it), so it keeps evaluating once per bar using that bar's own close, a deliberate caller-level live/backtest divergence of the same kind this doc already sanctions for touch resolution. One related pitfall this rewrite fixed: the realized-vol IV estimate must exclude the still-forming last bar from its lookback array (`bn_candles[:-1]`) even though the live tick is used elsewhere in the same function — otherwise a return spanning only a few seconds gets annualized as if it were a full closed 5m bar's move.
- **`BNTrade.current_premium`/`current_iv`** are refreshed on every `_tick_exits` cycle (even when not exiting) purely for the live dashboard mark — don't confuse this with `entry_premium`/`exit_premium`, which are the two values that actually determine `pnl`.
- **JSONB reads:** asyncpg returns `jsonb` columns as strings — decode with `_decode_jsonb` (see `database.py`) on any new read path.
- **Position rows are day-scoped in SQL:** `get_today_positions` filters on `(created_at AT TIME ZONE 'Asia/Kolkata')::date` (backed by an expression index); `update_position_exit` now keys on `order_id` (not `symbol` — every row's symbol is just `"BANKNIFTY"`, so `order_id` is the only thing that disambiguates same-day trades).
- **Options cost model rates are placeholders** (`BN_COST_*` settings) — not verified against current India options STT/exchange-txn figures. Safe for relative backtest signal quality (win rate, R-multiple), not yet for trusting absolute ₹ P&L.
- **Frontend DOM diffing:** `dashboard.js` maintains cell-level diffing via `_setCell(td, html, cls)` (no-ops when content is unchanged) and coalesces WS pushes into one paint per animation frame (`scheduleRender` + `requestAnimationFrame`). Do not replace this pattern with `tbody.innerHTML = ...` — it re-introduces flash.
- **Secrets:** `.env` is gitignored; never put real keys in `config.py` defaults or `.env.example`.

## Conventions for edits

- Keep `git` commits/pushes only when asked. `.env` must never be committed.
- Match the existing style: keyword-only dataclass construction, module-level `import app.config as cfg`, IST via `ZoneInfo("Asia/Kolkata")`.
- After changes, run `python3 -m py_compile` over the touched files (no test suite exists).
- Live and backtest **must** share the strategy core (`bn_entry_exit.evaluate_entry`/`evaluate_exit`, `bn_pricing.*`, `scalp_signals.*`); don't fork the decision logic.
