# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **Bank Nifty options paper-trading** app (FastAPI), ported from a standalone JS prototype (`c.html`). It streams live 5-minute BankNifty + 6 leader-stock data over WebSocket, evaluates a leader-momentum + composite-indicator strategy **tick-by-tick**, decides BUY (long ATM Call) / SELL (long ATM Put), simulates the option leg's premium via **synthetic Black-Scholes pricing** (no real options-chain data anywhere — see "Options pricing" below), and persists everything to PostgreSQL. It also has a **backtest** engine that replays the identical strategy on historical data.

Single process, single Uvicorn worker by design — all state lives in one in-process singleton (`AppState`). At most **one active trade** at a time (matches the source prototype — no concurrent positions).

**Everything strategy-related is runtime-dynamic.** All tunables (gates, risk, pricing, costs, session timings, tick cadence) are editable live from the `/settings` page — no restart — persisted in the `app_settings` table and re-applied on startup. Backtests accept per-run strategy overrides that never touch live values. See "Dynamic settings layer" below.

## Run

```bash
# Docker (recommended — builds the TA-Lib C library)
cp .env.example .env          # set POSTGRES_DSN
docker compose up -d --build
docker compose logs -f app    # watch the phase driver

# Local (needs the TA-Lib C library installed first, plus a reachable Postgres)
pip install -r requirements.txt
python main.py                # serves http://0.0.0.0:8080
```

- Dashboard: `http://localhost:8080` when run locally via `python main.py`; via Docker Compose it's host port **8001** (mapped to the container's 8080 — see `docker-compose.yml`), i.e. `http://localhost:8001`. An optional `caddy` sidecar (same compose file) also fronts the app with a self-signed HTTPS cert on `:8443`, purely so the dashboard's browser-notification alerts (which require a secure context) work over the LAN — see `static/js/alerts.js`.
- `TA-Lib` (the Python pkg) needs the **native C library** present at build time — the Dockerfile compiles it; for a local venv install it on the host first (`brew install ta-lib`, or build from source).
- There is **no test suite**. Validate changes with `python -m compileall -q app main.py` and by reading the flow.

## Architecture / daily flow

Driven by `scheduler.SchedulerService._phase_driver` (IST wall clock):

1. **09:00 PRE_MARKET** — no-op. The universe is a static config constant (`cfg.BN_INDEX_TOKEN` + `cfg.BN_ALL_STOCKS`), not fetched — there's nothing that can fail here (unlike the deleted equity engine's Gemini/watchlist screen).
2. **09:15 WAIT_ZONE** — `_load_all_historical()`: fetches 5 days of 5m history for the BN + NF stocks (fully archived, works fine) and MERGES (never replaces) today's BankNifty/Nifty 50 bars into whatever's already accumulated in `st.bn_index_candles_5m`/`st.nf_index_candles_5m` from prior live sessions — see the historical-archive note above. Then `market_data.start()` subscribes to the combined BN (15 tokens, 14 stocks + index) + NF (51 tokens, 50 stocks + index, 11 shared with BN) universe — 55 symbol-interval pairs total, past the server's documented ~40-entries-per-connection buffer limit. Since 2026-09-16/17 (the Nifty 50 universe grew from 32 toward its full 50 official constituents in stages — 3 early additions, LTIMindtree/Nestle India/ONGC, were removed after a vendor query confirmed zero data, and 3 more, InterGlobe Aviation/Jio Financial Services/Max Healthcare, were added after a user-supplied official constituent list and a vendor query both confirmed them — and BankNifty's grew from 11 to its full real membership of 14, after a 2026-09-17 correction against the live NSE factsheet showed the real index has 14 members, not 12, and Union Bank of India/Yes Bank had been miscategorized as non-index "extras"; 11 other non-index banking/financial extras were briefly tracked too but removed the same day per explicit user decision to track only real index members) this is split across **multiple WS connections** (`cfg.WS_MAX_FILTERS_PER_CONN` filters per connection, each with its own independent retry loop) — mirroring the deleted equity engine's split primary/secondary approach. `MarketDataService._process_tick` is fully synchronous (no `await`), so concurrent connections calling it from different asyncio tasks on the same event loop can never interleave mid-update — the existing `threading.Lock`s stay correct unchanged.
3. **09:30–15:00 ACTIVE** (then 15:00–15:30 CUTOFF, exits only) — `_run_active_phase()` is a **tick-wise loop** every `TICK_EVAL_INTERVAL_MS` (default 100ms), running directly on the event loop (no thread pool — only 12 instruments, unlike the equity engine's hundreds):
   - `_tick_exits` — if a trade is open, ratchet the trailing/breakeven stop and check target/stop against the live BankNifty price every cycle (this is also where the live option-premium mark is refreshed for the dashboard — Black-Scholes is closed-form, cheap enough to recompute every 100ms).
   - `_tick_entries` — wall-clock bar-close detection: tracks `st.last_evaluated_bar`; the instant the BankNifty 5m candle list's last bar changes to a NEW bar, evaluates exactly once against that just-closed bar (`bn_entry_exit.evaluate_entry`). No polling/pending-signal latch needed (the deleted JS prototype needed one because it only polled every 3s; 100ms is fast enough to catch a bar close directly).
4. **15:30 CLOSED** — `_run_eod()` squares off any survivor, writes `daily_stats`, **saves today's accumulated BankNifty bars to `bn_index_bars`** (the self-recording archive), persists `funds`, and resets per-day state. **`st.bn_index_candles_5m` is NOT cleared** — see below. `st.candles_5m` (individual stock candles) is **re-fetched via `_load_all_historical()`, not just cleared** (2026-09-16, explicit user decision) — the vendor fully archives multi-day history per stock, so the Stock Candles panel keeps showing real data through the closed session instead of going blank until the next 09:15 reload; a failed re-fetch just leaves the prior day's already-good data in place rather than blanking it.

Strategy core (shared by live **and** backtest, keep it that way): `bn_signals.*` (gates) → `bn_entry_exit.evaluate_entry` / `evaluate_exit` → `bn_pricing.*` (strike/expiry/premium).

**c.html has no working backtest** (`runBacktest()` there is a confirmed empty stub) — this repo's backtest engine is a fresh design, not a port of anything, but it drives the exact same `evaluate_entry`/`evaluate_exit` functions the live scheduler calls. One deliberate improvement over what a literal port of the source's `checkExit` would have done: the backtest resolves SL/target touches with gap-at-open + intrabar high/low (see `app/backtest/fills.resolve_index_touch`), not a close-only check — there's no reference implementation to preserve fidelity with, so it follows this repo's own existing (equity-era) convention instead.

**Entry condition (2026-09-19, explicit user decision — REPLACED the prior multi-gate sequence entirely):** of the 14 real NIFTY BANK stocks (`cfg.BN_ALL_STOCKS`), if at least `BN_SAME_DIRECTION_REQUIRED` (default 9) close the SAME direction (green or red) on the just-closed 5m bar, fire in that direction — BUY (long ATM Call) on ≥9 green, SELL (long ATM Put) on ≥9 red. That's the entire condition now; cooldown (`BN_ENTRY_COOLDOWN_S`) is the only other gate retained. The prior sequence — sideways-range filter (`BN_SIDEWAYS_RANGE_MIN`) → momentum filter → 6-leader direction vote → per-leader volume-surge count → composite BN indicator gate (RSI/MACD/EMA/pattern scoring) — is gone from `evaluate_entry`; those config constants and `bn_signals.py`'s gate functions are left in place but unused (see the "UNUSED" comments in `config.py`) rather than deleted, in case this ever needs reverting. `scheduler._tick_entries` now builds its stock-candle dict from `cfg.BN_ALL_STOCKS` (14), not `cfg.BN_LEADER_STOCKS` (6) — `app/backtest/engine.py`'s `_leader_recent_at` was updated the same way, since backtest shares `evaluate_entry` and would otherwise silently never fire (6 stocks can never reach a 9-stock threshold). Target/stop also changed alongside this, from 35/18 points to a much tighter **1/10** (`BN_TARGET_POINTS`/`BN_STOPLOSS_POINTS`) — `BN_BREAKEVEN_TRIGGER`/`BN_TRAIL_TRIGGER` (12/18) are now effectively inert since they're larger than the 1pt target. BUY → long ATM Call; SELL → long ATM Put. Always exactly 1 lot (`cfg.BN_LOT_SIZE = 30`) — no position sizing formula, unlike the old equity engine's risk-based `calc_quantity`. **Nifty 50's entry logic (`nf_entry_exit.py`) is UNCHANGED** — this replacement was BankNifty-only, an explicit scope decision.

**"Strong quantity" gate:** a literal port of the source's fixed absolute per-stock threshold (`cfg.BN_STOCK_QTY_THRESHOLD`), compared against `Candle.last_qty` — the real per-trade quantity embedded in the vendor's current-protocol tick payload (parsed from the `quote` field's `"...qty N..."` text in `market_data.py`). An earlier vendor protocol had no per-tick quantity at all (only cumulative 5m bar volume, hundreds of thousands — wildly mismatched against these tens/hundreds-scale thresholds), which made this gate a permanently-satisfied no-op; that limitation no longer applies since the vendor migrated its protocol (2026-07-23) and now exposes a real per-trade qty field.

**Exit:** target/stop/breakeven/trailing on the underlying BankNifty index price (points, frozen at entry from `cfg.BN_TARGET_POINTS`/`BN_STOPLOSS_POINTS`/`BN_BREAKEVEN_TRIGGER`/`BN_TRAIL_TRIGGER`/`BN_TRAIL_DISTANCE` — a later Settings change never retroactively alters an already-open trade). Settlement is the **option premium P&L × lot size**, not raw index points (`(exit_premium - entry_premium) * 30`) — index points are kept on the trade only as a diagnostic (`index_pnl_points`).

**Options pricing — fully synthetic, no real option-chain data:** ATM strike = `round(spot/100)*100`; expiry = **the LAST TUESDAY of the current/next month, 15:30 IST** (`bn_pricing.get_next_expiry` — see the expiry-day note below; this was "next weekly Thursday" until a 2026-09-19 fix); premium = standard Black-Scholes off BankNifty spot + a realized-volatility estimate from its own 5m bar-close log-returns (annualized via 75 bars/day × 252 days/year — a deliberate deviation from the source's tick-based estimator, required so live and backtest can share one `estimate_iv` implementation; backtest has no tick stream to replay). Risk-free rate, IV bounds, and default IV are all dynamic settings. See `app/engine/bn_pricing.py`. Nifty 50's own `nf_pricing.get_next_expiry` is a SEPARATE function (next Tuesday, weekly) — see the expiry-day note below for why these two genuinely diverged and are no longer shared.

**Expiry-day fix (2026-09-19, confirmed via web search + a real user-supplied example option symbol):** NSE changed its index-options expiry-day convention effective 2025-09-01 — Nifty 50 weekly expiry moved from Thursday to **Tuesday**, and **BankNifty's weekly contracts were discontinued entirely**, leaving only monthly/quarterly, with that expiry day also moved to the **last Tuesday** of the month. `bn_pricing.get_next_expiry`/`nf_pricing.get_next_expiry` were still using the old "next Thursday, weekly" rule for BOTH instruments until this fix — a real correctness bug affecting every Black-Scholes premium calculation in the engine (live and backtest), not just the option-symbol/real-LTP features. Because the real-world cycles now genuinely differ (BN monthly vs. NF weekly), `get_next_expiry` and the option-symbol builder are no longer shared between the two pricing modules — `bn_pricing.build_monthly_option_symbol` (`UNDERLYING+YY+MMM+STRIKE+CE/PE`, e.g. `"BANKNIFTY26SEP56400CE"`, no day-of-month since a monthly contract's expiry day is implied) vs. `nf_pricing.build_weekly_option_symbol` (`UNDERLYING+YY+M+DD+STRIKE+CE/PE`, `M` a single-char month code 1-9/O/N/D, e.g. `"NIFTY2692223250PE"` — confirmed correct against a real user-supplied example). Reusing one function for both would silently be wrong for whichever one changed — don't re-merge them.

**Self-recorded BankNifty history:** because the market-data server never provides BankNifty index history via the REST API (see above — now returns nothing at all, not even "today"), `scheduler._run_eod` writes the day's accumulated `bn_index_candles_5m` buffer into the `bn_index_bars` table every day (idempotent upsert by `start_time`) — since 2026-07-23 this buffer is populated by the synthetic index (see above) rather than real vendor ticks, but the recording pipeline itself is unchanged. `app/backtest/data.load_backtest_data` reads BankNifty history **from this table**, not from the REST API — the runnable backtest date range grows by one day at a time as the live engine runs, now backed by synthetic bars for any day recorded after the migration. The 11 BN stocks ARE fully archived on the external server, so they're still fetched directly for every backtest run.

## Dynamic settings layer

- `app/config.py` holds **static** system values (endpoints, DSN, the BN instrument universe, pool/buffer sizes, lot size) as plain attributes, and **dynamic** tunables in `_DEFAULTS`, resolved via module `__getattr__` with precedence: *thread-local overrides (backtest run) → runtime overrides (Settings page / DB) → default*. `cfg.X` therefore always returns the current value.
- **Never copy a dynamic `cfg.X` into a module-level constant or default-argument value** — it freezes at import and silently stops being dynamic. This is why `BNTrade`/`BTPosition` **freeze** their risk parameters (target/stoploss/breakeven/trail) from cfg exactly once, at entry (`bn_entry_exit.open_trade_from_signal`) — that's a deliberate snapshot for correctness (an open trade's economics must not shift under it), not the anti-pattern the rule above warns about.
- **Adding a tunable = two places:** a default in `config._DEFAULTS` **and** a SPEC entry in `app/services/settings.py` (label/type/bounds/group/`bt` flag). Time-of-day settings are virtual `"HH:MM"` SPEC keys expanded to their `*_HOUR`/`*_MIN` config pairs. An import-time assertion in `settings.py` raises `RuntimeError` if the two ever drift.
- `cfg.thread_overrides(...)` may only be entered in **backtest worker threads** (`_simulate_day`), never on the event loop.
- Backtest per-run overrides: `POST /api/backtest {overrides: {SPEC_KEY: value}}`, validated with `expand_changes(bt_only=True)` (only `bt: True` SPEC entries), recorded in `backtest_runs.params`, applied via `cfg.thread_overrides` inside each day worker.
- Settings API: `GET /api/settings` (grouped describe), `PUT /api/settings {changes}` (validate → persist atomically (`replace_app_settings`, one transaction) → apply; a value equal to its default deletes the override row), `POST /api/settings/reset {keys?}`. Session-time changes are cross-validated (`validate_time_order`); indicator-period combos are cross-validated (`validate_bn_indicator_periods`, e.g. MACD fast < slow, lookback ≥ what RSI/EMA/MACD need to converge) on save, on partial reset, and at startup load (self-heals to defaults).

## Hard conventions — get these wrong and it breaks

- **Keying:** `candles_5m` is keyed by **TOKEN** (trading-symbol string) — the 14 BN stocks only, the real NIFTY BANK index's full membership (2026-09-16 addition of Bank of Baroda/Union Bank of India/Yes Bank + a 2026-09-17 correction; 11 non-index banking/financial extras were tracked briefly the same day then removed, per explicit user decision to track only real index members); the BankNifty index has its OWN dedicated field, `bn_index_candles_5m` (a plain list, not a dict), with its own lock `st._bn_index_lock`. `ltp` is keyed by **SYMBOL NAME**; the index's live price is the separate `st.bn_index_ltp` float. Don't conflate the two — there is deliberately no extra entry in `candles_5m`/`ltp` for BankNifty itself.
- **`st.bn_index_candles_5m` is never cleared at EOD** (unlike everything else, which resets daily) — it's the ONLY source of multi-day BankNifty depth (the composite indicator gate needs `BN_INDICATOR_LOOKBACK_BARS`, default 200, bars to converge; the external server can never supply more than ~75 bars/day). It persists and grows across real trading days within one long-running process, capped at `MAX_CANDLE_BUFFER` (300 bars, ~4 sessions). A restart loses it; `_load_all_historical`'s merge-not-replace logic (via `MarketDataService._upsert_list`) is what lets it survive a same-process day rollover.
- **Single active trade.** `st.active_trade: Optional[BNTrade]` — not a dict. Closing sets it to `None` and appends to `st.closed_trades`. There is no concurrent-position concept anywhere in this engine (deliberately, matching the source).
- **Locking:** `candles_5m` token locks and `_bn_index_lock` guard the WS-thread-vs-event-loop boundary — `MarketDataService._process_tick` (WS callback context) and the scheduler's tick loop are the only two touchpoints, and both go through `st.candle_lock(token)` / `st._bn_index_lock`.
- **Candle lists are strictly chronological.** `market_data._upsert`/`_upsert_list` update the in-progress bar on an equal `start_time`, append on a newer one, and **drop** stale out-of-order bars (reconnect replays). `_load_all_historical`'s catch-up merge reuses `MarketDataService._upsert_list` directly (not a second copy) so there's exactly one implementation of "how a BankNifty bar gets folded in," whether it arrives via WS tick or REST catch-up.
- **TA-Lib inputs:** pass raw NumPy `float64` arrays, never DataFrames, into `bn_signals.py`'s RSI/EMA calls. `bn_signals.bn_composite_indicator`'s MACD is **not** `talib.MACD`(which would force a signal line) — it's two plain `talib.EMA` calls subtracted, matching the source's raw EMA12-EMA26 zero-cross with no signal line at all.
- **Shared decision core, not just shared formulas:** `bn_entry_exit.evaluate_exit` reads risk parameters (target/breakeven/trail) FROM THE TRADE OBJECT it's given, not from `cfg` — and it's called with either a live `BNTrade` (`app/models.py`) or a backtest `BTPosition` (`app/backtest/portfolio.py`) interchangeably, because the two dataclasses share the exact field names `evaluate_exit` touches (`direction`, `entry_index_price`, `current_sl`, `sl_stage`, `target`, `trail_trigger`, `trail_distance`, `breakeven_trigger`, `strike`, `option_type`, `expiry`). Don't rename a field on one without the other — this duck-typing is how backtest and live stay provably in sync without a shared decision function needing two call signatures.
- **No look-ahead in backtest:** at bar `t` an entry uses only bars `[..t]`; IV/expiry/premium are computed from bar `t`'s own timestamp and closes `[..t]` only. A position opened at bar `t` exits only on bars `> t`. Backtest is **intraday-only** (fresh portfolio per day, EOD square-off, days run in parallel) — there is no positional/delivery/1d mode (nothing in the source ever holds an option position overnight).
- **Options are cash-only, always exactly 1 lot** — there is no leverage/margin concept and no quantity-sizing formula anywhere in this engine (unlike the deleted equity engine's `calc_quantity`/`INTRADAY_LEVERAGE`).

Backtest is triggered from the dashboard: `POST /api/backtest {from_date, to_date, slippage_bps?, overrides?}` runs in a background task and is polled via `GET /api/backtest/{id}`; results export at `…/export.csv`. There is no `timeframe`/`mode`/`capital` field — backtest is always 5m/intraday/1-lot.

**Stock Candles panel (`bn_breakout.py` + the dashboard's `stockCandles`/`globalSignal`/`breakout`/`srLevels` payload fields)** is a c.html UI-parity port — a breakout/support-resistance scanner and `BN_INDEX_WEIGHTS`-weighted global signal over the same 12-instrument universe the BN strategy already streams. It is purely informational and **never** feeds `evaluate_entry`/`evaluate_exit` — don't wire it into the trading decision. 5m S/R is computed on the fly from in-memory candles every `STATE_UPDATE`; 15m S/R comes from a separate periodic REST refresh (`SchedulerService._refresh_15m_sr_loop`, every 5 min) since this app otherwise never streams/fetches 15m candles — the live WS subscription filters stay 5m-only.

**The Kite-style manual-order form (`js/kiteForm.js`) is wired to the real paper-trading engine** (explicit user decision, 2026-09-01, reversing the form's original c.html-parity decorative-only behavior; generalized to BOTH instruments 2026-09-18 — NF manual trading didn't exist before that, and the form's markup had been dropped from `index.html` entirely along with the old Trade Dashboard panel, leaving the JS a silent no-op for a while):
- Submit calls `POST /api/manual-order`/`/api/manual-order-nf {direction}`; Exit calls `POST /api/manual-exit`/`/api/manual-exit-nf` (all in `app/api/dashboard.py`). These place/close the exact same `st.active_trade`/`st.active_trade_nf` the automated strategy uses — `app/services/bn_trade.py`/`nf_trade.py`'s `place_manual_order`/`force_close(..., label="MANUAL EXIT")` — a manual trading-desk override on the SAME single-trade slot per instrument, not a second/parallel trade concept. `place_manual_order` bypasses `evaluate_entry`'s strategy gates (it's a human decision, not an algo signal) but still goes through `open_trade_from_signal`, so risk parameters freeze from cfg exactly like an algo-fired trade, and lot size is always `cfg.BN_LOT_SIZE`/`NF_LOT_SIZE` (this engine has no position-sizing concept — the form's Qty field is fixed/display-only). Strike/expiry/premium are computed server-side via the real `bn_pricing.py`/`nf_pricing.py` (ATM strike off the live spot, realized-vol IV estimate) — there is no client-side pricing preview anymore, and like an algo-fired trade it also picks up the real-option-LTP feature below once a tick arrives. Order Type (Market/Limit) is cosmetic only: every fill in this engine is a synthetic Black-Scholes mark at submit time (until a real tick arrives), there's no real order book for a limit price to rest on. `js/kiteForm.js` uses the same `ids`-object pattern as `STOCK_IDS_BN`/`STOCK_IDS_NF` etc. elsewhere (`KITE_IDS_BN`/`KITE_IDS_NF`) rather than a second copy of the file.
- The Local Trade Log (browser IndexedDB, in `dashboard.js`) is a second, browser-only record of the REAL server trades (mirrored from `STATE_UPDATE`'s `activeTrade`/`closedTrades`, manual or algo-originated alike), kept deliberately separate from "Today's Trades" (the real, Postgres-backed history) rather than reading `/api/positions`. Its IndexedDB store is keyed by a derived `localId` (`${orderId}_ENTRY`/`${orderId}_EXIT`) and written with `put()`, not `add()` — a page reload always re-delivers the current trade state, so idempotent overwrite (not an in-memory dedupe set, which can't survive a refresh) is what prevents duplicate rows.

**Live ATM CE/PE quote (2026-09-18, explicit user decision)** — `evaluate_entry` (in both `bn_entry_exit.py`/`nf_entry_exit.py`) now computes the current ATM strike and Black-Scholes CE/PE premiums UNCONDITIONALLY, every closed bar, regardless of whether the entry gates actually pass — previously this was only computed inside the `if buy_ready or sell_ready:` block, so it stayed blank almost all the time. Exposed on `BNDiagnostic`/`NFDiagnostic` as `atm_ce_premium`/`atm_pe_premium` (alongside the pre-existing `atm_strike`/`atm_iv`; `atm_premium` is kept as a CE-value alias for the still-unused Entry Loop Monitor UI), sent in `STATE_UPDATE`'s `entryLoop`/`entryLoopNf.atmCePremium`/`atmPePremium`. This is a theoretical Black-Scholes estimate only, not real option-chain data — superseded in the UI by the live ATM watchlist below wherever real data actually flows.

**Live ATM CE/PE watchlist (2026-09-18, explicit user decision)** — a continuous REAL-market-LTP subscription for whatever the CURRENT at-the-money strike is, shown regardless of whether a trade is open. Distinct from the real-option-LTP paper-trading feature above: that one tracks ONE trade's option symbol, FROZEN at the strike it entered on; this one tracks the LIVE, moving ATM strike, recomputed continuously off `st.bn_index_ltp`/`nf_index_ltp`. `SchedulerService._tick_atm_watch` runs every `TICK_EVAL_INTERVAL_MS` tick (cheap — `get_atm_strike` is just `round(spot/100)*100`, no Black-Scholes) but only touches the WS subscription when the strike actually changes, via `MarketDataService.set_bn_atm_watch`/`set_nf_atm_watch` — a THIRD pair of slots on the same dedicated option WS connection `_resync_option_connection` already manages (alongside `_bn_option`/`_nf_option` from the per-trade feature), merged into one filter set. `_process_tick` matches ticks against `st.bn_atm_ce_symbol`/`bn_atm_pe_symbol`/`nf_atm_ce_symbol`/`nf_atm_pe_symbol`, writing into `st.bn_atm_ce_ltp`/`bn_atm_pe_ltp`/`nf_atm_ce_ltp`/`nf_atm_pe_ltp` — no one-way latch here (unlike the per-trade feature), since there's no single trade's entry value to freeze; a strike change always resets the cached LTPs to `None` rather than showing a stale, wrong-strike price. Sent in `STATE_UPDATE` as `bnAtmWatch`/`nfAtmWatch` (`{strike, ceSymbol, peSymbol, ceLtp, peLtp}`), rendered by `dashboard.js`'s `renderAtmWatch()` — a small always-visible watchlist row per Active Trade panel, showing "waiting for live tick" until the first real tick for that strike arrives. Torn down at EOD (`_run_eod` calls `set_bn_atm_watch(None, None)`/`set_nf_atm_watch(None, None)`) — no point holding a subscription for a stale strike once the market's closed.

**Server-side price alerts (`app/services/price_alerts.py`)** — the leader-consensus price-move alert (N of BN's 6 / NF's 12 leaders each crossing their own `BN_PRICE_ALERT_PTS_*`/`NF_PRICE_ALERT_PTS_*` points threshold, in the SAME direction, on the same live bar) used to be computed entirely client-side, once/sec, off `STATE_UPDATE` — meaning it only ran while a dashboard browser tab was open, and could miss a fast in-and-out move between STATE_UPDATE ticks. As of 2026-09-09 (explicit user decision) the check itself moved server-side into `SchedulerService._tick_alerts`, called every `TICK_EVAL_INTERVAL_MS` tick alongside `_tick_exits`/`_tick_entries` — same cadence and same `st.candles_5m` read path the trading engine itself uses, just a separate, purely-informational check that never touches `evaluate_entry`/`evaluate_exit`. When the condition fires, the server pushes an `ALERT` WebSocket message (see the table below); the browser's job (`static/js/alerts.js`'s `handleServerAlert`) is now just to display it. The edge-trigger state (`_was_consensus`, keyed `"BankNifty:up"` etc.) lives as module-level state in `price_alerts.py` — safe unlocked because, like `st.last_evaluated_bar`, it's only ever touched from the tick loop on the event loop, never from the WS ingest thread. The client still independently computes the SAME per-leader crossed/direction data purely for the live "X/N leaders crossed" badge next to the Global Signal (`checkPriceAlerts`/`_renderThresholdBadge` in `alerts.js`) — that's cosmetic display only, not the alert-firing path anymore.

**Real-option-LTP paper trading (2026-09-17, explicit user decision, LIVE ONLY — backtest is unaffected)** — both automated engines (BN and NF) settle every trade's P&L off the option's **real market LTP** instead of a purely theoretical Black-Scholes mark, wherever a real tick is actually available:
- `entry_premium` is ALWAYS the Black-Scholes value from `evaluate_entry` (in `bn_entry_exit.py`/`nf_entry_exit.py`, unchanged) — a real tick for a trade's specific strike/expiry cannot exist yet at the exact instant the trade fires, since the option symbol isn't subscribed to until the trade is confirmed open (an explicit user decision — the alternative, delaying entry by ~1-2s to wait for a first real tick, was rejected in favor of no added entry latency).
- The moment the trade opens, `bn_trade.place_paper_order`/`nf_trade.place_paper_order` call `MarketDataService.set_bn_option_symbol`/`set_nf_option_symbol(trade.option_symbol, trade.option_symbol)`, which dynamically subscribes that one option instrument on a THIRD, separate WS connection (`market_data.py`, `_resync_option_connection`) — distinct from the two fixed BN+NF-universe connections, since its filter list changes every time a trade opens/closes rather than being fixed once at startup. The vendor protocol has no observed "add one more subscription" message, so a change here tears down and reconnects just this one connection with a fresh filter list.
- `MarketDataService._process_tick` recognizes a tick whose `stock_symbol` matches `st.active_trade.option_symbol`/`st.active_trade_nf.option_symbol`, updates `st.bn_option_ltp`/`st.nf_option_ltp`, and flips `trade.premium_synthetic` from `True` to `False` — a **one-way latch per trade** (same pattern as the synthetic-index-to-real-tick latch in `_update_synthetic_index`). Option ticks never touch `candles_5m`/`ltp` (those stay "the fixed BN/NF stock universe only").
- `bn_trade.py`/`nf_trade.py`'s `_live_premium()` helper reads `trade.premium_synthetic`: while `True` (no real tick has arrived yet, typically only for the first second or two of a trade), `current_premium`/`exit_premium` keep using the Black-Scholes value `evaluate_exit` always computes (a harmless, always-available fallback); once latched `False`, they use the real LTP instead. `evaluate_exit` itself is untouched — the shared decision core's target/stop logic reads only the underlying INDEX price, never the premium, so this override happens entirely at the CALLER level (`bn_trade.py`/`nf_trade.py`), per this repo's "don't fork the shared functions" convention.
- The option instrument symbol is built by `bn_pricing.build_monthly_option_symbol`/`nf_pricing.build_weekly_option_symbol` (no longer one shared function — see the expiry-day fix note under "Options pricing" above for why) using `cfg.BN_OPTION_UNDERLYING`/`cfg.NF_OPTION_UNDERLYING` ("NIFTY", deliberately NOT `NF_INDEX_TOKEN`'s "NIFTY 50").
- **This vendor DOES stream real option data — but ONLY at 1-MINUTE granularity, not 5m like everything else in this app** (confirmed 2026-09-18, after two earlier rounds of testing at `"5m"` wrongly concluded the vendor carries no option data at all — a real user-supplied screenshot showing live option quotes from the same API, with only "1m" checked, is what actually surfaced this). Two bugs, both now fixed: (1) `MarketDataService._resync_option_connection` always requested `"interval": "5m"` for option/watch filters — now `"1m"`; (2) `_process_tick` required `interval == "5m"` UNCONDITIONALLY before it even checked which symbol a tick belonged to, which silently discarded every real option tick regardless of what was subscribed — the option/watch symbol-match check now runs first, and only requires `interval == "1m"` for that branch specifically (the fixed BN/NF universe still requires `"5m"`, unchanged). Also fixed: the `stockname` sent for an option filter must be the underlying's plain name ("NIFTY"/"BANKNIFTY"), not the option symbol repeated — confirmed from the vendor's own echoed tick data (`'stockname': 'NIFTY'` on every option tick, regardless of strike/type).
- Both bugs were masked by an unlucky pattern: every early empirical test (numeric exchange_token, wrong stockname, format guesses, wide-date REST lookbacks) used `"5m"` throughout, since that's the convention everywhere else in this app — so every test failed the same way regardless of what else was varied, producing consistent-looking but wrong evidence of "no option data at all." If option ticks ever stop arriving again, check the interval field FIRST before re-litigating the symbol format.
- Backtest is completely unaffected: `BTPosition` (`app/backtest/portfolio.py`) has no `option_symbol`/`premium_synthetic` fields, and nothing in the backtest replay loop calls `market_data.py` or `bn_trade.py`/`nf_trade.py` (those are live-only, under `app/services/`) — it keeps using the pure Black-Scholes model exactly as before.

## WebSocket broadcast types

The `/ws/dashboard` endpoint broadcasts three distinct message shapes — `dashboard.js`'s `ws.onmessage` dispatches on `type`:

| `type` | Cadence | Payload |
|--------|---------|---------|
| `STATE_UPDATE` | 1 s | Full dashboard payload: `clock`, `phase`, `wsStatus`, `apiStatus`, `bnLtp`, `dailyPnl`, `funds`, `activeTrade`, `closedTrades`, `entryLoop` (the `BNDiagnostic` — the "why didn't it fire" panel), `stockCandles`/`globalSignal`/`weightedRedGreen`/`breakout` (BN + NF), etc. |
| `TICK_UPDATE` | ~100 ms | `{prices: {name: ltp, ...}}` — a live-price delta, feeds the Stock Candles panel's live cell flash + the local qty-audit IndexedDB log (`static/js/breakout.js`/`qtyAudit.js`) |
| `ALERT` | on fire (edge-triggered) | `{title, body}` — pushed by `SchedulerService._tick_alerts` (via `app/services/price_alerts.py`, checked every `TICK_EVAL_INTERVAL_MS` tick) the instant the leader-consensus price-move condition fires; `static/js/alerts.js`'s `handleServerAlert` just displays it as a browser Notification/toast. Moved server-side 2026-09-09 (explicit user decision) so it no longer depends on a dashboard browser tab being open to notice — see the "Server-side price alerts" note below. |

## Gotchas & known limitations

- **The BankNifty history-archive limitation (see "External dependencies" above) is the single most important thing to remember when touching backtest or the historical loader.** If a backtest run fails with "no self-recorded BankNifty history," that's expected until the live engine has run at least one full day in this environment — it is NOT a bug to "fix" by fetching a date range from the REST API.
- **Kotak Bank naming:** `cfg.BN_ALL_STOCKS["KOTAK BANK"] = "KOTAKBANK"` — the dict KEY (stockname text) must be `"KOTAK BANK"`, NOT `"KOTAK MAHINDRA BANK"`. The market-data server matches by exact stockname text; confirmed by direct testing that the "Mahindra" variant silently returns zero candles for the identical, correct token/symbol.
- **South Indian Bank naming (same gotcha class, 2026-09-17):** if `"THE SOUTH INDIAN BANK"` (note the leading "THE", per the vendor's own instrument-master export) is ever re-added to `cfg.BN_ALL_STOCKS`, use that exact text — it's not currently tracked (removed 2026-09-17 along with 10 other non-index banking extras, once the real NIFTY BANK index was confirmed to have 14 members, not 12; see the Architecture section above), but was live-tested at the time and worked fine under that name.
- **Entry is evaluated every tick, not once per bar (2026-09-22, explicit user decision — supersedes the composite-indicator-gate-era claim that used to be here).** `evaluate_entry` (BN and NF alike) is called every `TICK_EVAL_INTERVAL_MS` (~100ms) from `_tick_entries`/`_tick_entries_nf`, not gated on a bar closing — the old `last_evaluated_bar`/`last_trade_candle` dedup state was removed (`state.py`). The basket VWAP-momentum score's "current price" side now reads the LIVE tick (`current_index_price`/`basket_ltp` params, fed from `st.bn_index_ltp`/`st.ltp`), so a real move can fire a trade within ~100ms instead of waiting up to 5 minutes for the next bar close; VWAP itself still only moves at bar-close granularity (see `scalp_signals.py`). Re-entry after a fire is still fully gated by `st.active_trade is not None` plus the cooldown check inside `evaluate_entry`, so there's no risk of firing twice off one persistent signal. Backtest is unaffected — it never passes `current_index_price`/`basket_ltp` (no tick stream to give it), so it keeps evaluating once per bar using that bar's own close, a deliberate caller-level live/backtest divergence of the same kind this doc already sanctions for touch resolution. One related pitfall this rewrite fixed: the realized-vol IV estimate must exclude the still-forming last bar from its lookback array (`bn_candles[:-1]`) even though the live tick is used elsewhere in the same function — otherwise a return spanning only a few seconds gets annualized as if it were a full closed 5m bar's move.
- **`BNTrade.current_premium`/`current_iv`** are refreshed on every `_tick_exits` cycle (even when not exiting) purely for the live dashboard mark — don't confuse this with `entry_premium`/`exit_premium`, which are the two values that actually determine `pnl`.
- **JSONB reads:** asyncpg returns `jsonb` columns as strings — decode with `_decode_jsonb` (see `database.py`) on any new read path.
- **Position rows are day-scoped in SQL:** `get_today_positions` filters on `(created_at AT TIME ZONE 'Asia/Kolkata')::date` (backed by an expression index); `update_position_exit` now keys on `order_id` (not `symbol` — every row's symbol is just `"BANKNIFTY"`, so `order_id` is the only thing that disambiguates same-day trades).
- **Options cost model rates are placeholders** (`BN_COST_*` settings) — not verified against current India options STT/exchange-txn figures. Safe for relative backtest signal quality (win rate, R-multiple), not yet for trusting absolute ₹ P&L.
- **Frontend DOM diffing:** `dashboard.js` maintains cell-level diffing via `_setCell(td, html, cls)` (no-ops when content is unchanged) and coalesces WS pushes into one paint per animation frame (`scheduleRender` + `requestAnimationFrame`). Do not replace this pattern with `tbody.innerHTML = ...` — it re-introduces flash.
- **Secrets:** `.env` is gitignored; never put real keys in `config.py` defaults or `.env.example`.

## Conventions for edits

- Keep `git` commits/pushes only when asked. `.env` must never be committed.
- Match the existing style: keyword-only dataclass construction, module-level `import app.config as cfg`, IST via `ZoneInfo("Asia/Kolkata")`.
- After changes, run `python3 -m py_compile` over the touched files (no test suite exists).
- Live and backtest **must** share the strategy core (`bn_entry_exit.evaluate_entry`/`evaluate_exit`, `bn_pricing.*`, `bn_signals.*`); don't fork the decision logic. If live and backtest need different treatment of the same moment (e.g. intrabar SL/target touch resolution), do it at the CALLER level (the scheduler vs. the backtest replay loop), never by branching inside the shared functions themselves.
